# Static pytest fixture bindings

The resolver reads tracked Python syntax and resolves fixture registration without importing modules or running pytest. Tests request fixtures through parameters, function or class `pytest.mark.usefixtures`, literal module/class `pytestmark`, and visible `autouse=True` fixtures. Registrations come from ancestor `conftest.py` files, literal `pytest_plugins` declarations, imported fixture aliases, module fixtures and class fixtures. The nearest registration wins, including its autouse setting; a non-autouse override is applied only when requested. A fixture overriding a name can request the outer registration with the same name.

Fixture dependencies and literal `request.getfixturevalue` requests are followed transitively with cycle guards. Direct `pytest.mark.parametrize` arguments supply values and do not request same-name fixtures; `indirect=True` and literal indirect name lists retain fixture requests. Calls through fixture helpers, imports of production files, and literal reads of tracked production files become static `tests` edges from the test case. These edges include `via: fixture` and the fixture node id. Calls preserve their resolution confidence, imports use 0.5 and literal reads use 1.0. Fixture registration alone creates no tested-code binding, so a fixture that reaches no tracked production remains eligible for `unmatched_test`.

`testing_fixtures.link` exposes the selected fixture ids in `model.test_fixture_bindings` for supplemental mechanisms such as in-process HTTP clients. Python ASTs are shared with those mechanisms through `testing_static.python_modules`; source is parsed once per resolve. Dynamic fixture factories and dynamically computed plugin declarations cannot be inferred through this registration mechanism. Static links describe possible tested code, not execution coverage; ingested coverage remains the stronger evidence.

Fixture/helper bodies also use the bounded local path and dynamic import resolver and SQL glob selector. Supplemental evidence is indexed by the exact enclosing fixture/helper symbol, including registered plugin modules outside test directories. Requesting one fixture does not inherit a sibling fixture's file reads or migrations. Module-level reads remain visible to the fixtures whose modules perform them.

Relative SQL globs that match several possible working directories produce an `unsupported_test_mechanism` diagnostic and no tested-code edge. Fixture supplements use the same ambiguity rule as direct SQL contracts, with diagnostics retained for registered plugins outside test directories.
