# v0.1 scale check

Checked on 11 and 12 October 2026 against the read-only sample-monorepo and sample-saas repositories. Before is commit 46ea47a. After is the head of the `p95-scale-check` branch. Each command ran from inside the sample repository as `uv run --project <worktree> cbi ... --out <tmpdir>`, under `/usr/bin/time -l`. `git status --porcelain` was the same before and after every run, so the mapper wrote nothing in either repository.

## Setup

- sample-monorepo: about 13.4k tracked files in four workspaces. A scan parses 1,425 code files and keeps 12,471 docs, about 12,500 symbols and 11,200 test cases. It has no database. It has no agent concept map, so the runs used a generated one: one concept per top-level code folder (22 concepts, 8 relationships from cross-folder imports).
- sample-saas: about 9.8k tracked files. The runs used the concept map, screens and structure files from its own local `.cbi/`. The Database tab has 92 tables and the API endpoints tab has 456 endpoints.
- `cbi history` covered a short window, not three months. Three months is 1,143 points on sample-monorepo and about 130 on sample-saas, and before the fix every point kept a full model (see History below). Windows: sample-saas from 17 September (31 points), sample-monorepo from 3 October (14 points).
- `cbi diff` compared `HEAD~3` with `HEAD` in a model directory with nothing else in it.
- First paint used the same headless Chrome path as `cbi render` (`cbi.render`, `?render=1`). It reports first contentful paint and an upper bound for when the viewer sets its ready title, which is about 50 ms late because the title is polled.

The machine was shared with other jobs and reached a load average of nearly 400 during some runs. Wall time is shown, but CPU time (user plus system) is the fairer comparison: the before cold scan of sample-monorepo took 256 s of wall time but only 72 s of CPU.

### History

Before, every history point kept a full ref model: 54 to 95 MB per point on sample-saas and 128 to 356 MB on sample-monorepo. The 31-point sample-saas window wrote 2.7 GB of models, and a three-month run filled 6.6 GB before it was stopped. Copying the previous model as a seed added about 12 MB of free pages per model. On sample-monorepo history crashed at its first point: files with the same path in two submodules collided when concepts were projected.

After, ref scans share `refs/parse.db`, and history keeps only the newest point model. The same 31-point window peaked at 392 MB for the whole model directory, including the 80 MB working model and a 36 MB `parse.db`. On a 6-entry window the history JSON was byte-identical to the commit before this change, with 110 MB of models against 594 MB. sample-monorepo now runs at about 49 s of CPU per point and peaks at 1.5 GB on disk.

## Fixes

Each fix has a test in `tests/test_scale.py` or `tests/test_history.py` that fails on the code before it, except the ORM anchor check, which only skips searches that cannot match and is covered by the existing table-use tests.

| Hotspot | Found by | Fix |
|---|---|---|
| History projected concepts by workspace-relative paths, so `README.md` in two submodules collided and crashed the scan | sample-monorepo history | Project by paths from the top repo |
| `span_hashes` compiled a new regex per symbol (23k compiles thrashed the `re` cache) | cProfile of the sample-monorepo cold scan | Find the signature words with `str.find` |
| Python env-read detection walked parents on every syntax node (2.7M calls) | same | Check the node type first |
| Table-use extraction scanned every literal in every file, even with no tables | same | Skip a workspace with no tables |
| String and comment scanning in table-use extraction ran character by character | cProfile of the sample-saas diff | One compiled regex each, 7.7 times faster. The old scanner also lost a line after each backslash-newline inside a string, so a use could be credited to the file instead of its function |
| ORM patterns ran on files without their anchor word | cProfile of sample-saas history | Skip a pattern when its literal is absent |
| Test counts in the context block scanned every test edge per node | cProfile of the sample-monorepo build | Index test edges once |
| Table declarations and uses were recomputed for every commit history or diff scans | cProfile of sample-saas history | Cache by blob id in the process |
| History's folder fallback compared every file with every unowned file | same | Index files by folder |
| Each ref scan copied the previous model and history kept every point model | disk use of sample-saas history | Shared `refs/parse.db`; history drops point models it no longer needs |

The string scanner was compared with the old one over all 3,277 code files of both repos: literal text and comment masks were identical. 31 files differed only in line numbers, where the old scanner was short by one per backslash continuation. A sample-saas scan with the old and new code gave the same tables, columns, foreign keys and use counts. In two scripts the corrected line numbers moved two uses from file level to the functions that contain them.
